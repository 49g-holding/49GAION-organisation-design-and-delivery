# Upstream drafts

Drafts of proposals to 49GAION, found while writing the product blueprint `v0.1.0`. They are not proposed: a draft goes to 49GAION only on the governing seat's word, and then only by pull request. None of them changes a part here.

| # | Where | What was found | Draft |
|---|---|---|---|
| 1 | Standard §3.1, item 11; Naming Standard R9; the Library register | No text says where an assembly's blueprint lives, and no rule names a product repository. R9, addition 4, covers only the mother of a part whose first instance holds an organisation's data. The Products table of the Library register has no column for an assembly's own blueprint | An assembly's blueprint lives in its own public product repository, `49GAION-<product>`, recorded before it is created. The Products table pins it by repository, path, version, commit and SHA-256, as the Parts table pins a mother |
| 2 | Operating Protocol | There is no Protocol section for products, and no card or schema for one. "What the assembly itself sets" (`49GAION/DR-0025`, item 3) has no place in the Protocol | A short section on assemblies: the blueprint's fields (parts by pin, connections by contract, what it sets, one shared test), and the rule that a setting the assembly fixes is the same in every part that carries it |
| 3 | Protocol §13, item 10 | A source may stand beside Source Lifecycle, read only, but none may replace it until the Protocol names the new asking route. No route is named | Name the asking route a replacement source would use, or state that asking and filing always stay with Source Lifecycle even when another source serves the documents |
| 4 | The sockets contract of Source Lifecycle | The drafts are written for the Target Operating Model only: the needs request's `raised_by` lists only its parts, the filing receipt is `tom-filing-receipt`, and every `$id` sits under the Target Operating Model. Process and Position Design and Delivery and Implementation ask Source Lifecycle too, and file into it | Generalise the sockets contract under Source Lifecycle's own name, for every connected stage, when Source Lifecycle adopts it (its PRD D-20). The same points stand in Source Lifecycle's `contracts/README.md`, "Points for adoption" 1 and 2 |
| 5 | Protocol §17; §21, item 1 | Each stage "stands alone", but Process and Position Design needs a decided release in the Target Operating Model's format, with a hash-matched copy in Source Lifecycle; it has no way to take an operating model made elsewhere. Delivery and Implementation has one (mode B) | Either give Process and Position Design a mapping mode for an operating model made elsewhere, or state that it stands alone only on its side towards Delivery and Implementation |
| 6 | Protocol §19, item 11; §21, item 3 | The Target Operating Model and Process and Position Design send notices under their own contracts (`release-notice` v0.5 and v0.4). Neither pins the Library's release notice contract, which the Library card already names | Each stage's notice contract pins the Library's release notice contract and only narrows its fields (Standard §3.1, item 8) |
| 7 | The Library register; Protocol §21 | The Products row says Delivery and Implementation is "written in full (v0.2.0)" while its pin is v0.2.1. §21, item 10, lists a pin without its commit, while Standard §3.1, item 9, includes it. §21, item 11, still names TEST-DESIGN-CHAIN v1, while item 12 brings it to v2. The register's Connections column for this product omits the sockets contract of Source Lifecycle. Only Source Lifecycle is listed as a single part offered alone, while the Target Operating Model is "a product on its own" (Protocol §19, item 9) | Align these texts at the next release |
| 8 | The parts' own texts | The Source Lifecycle mother's §5.8 still names the sockets contract drafts of the Target Operating Model v0.4.0, and its §0 keeps a "Made from … part card `v1`" row beside the `v4` row. The Process and Position Design mother names its Library card v2 while the Library holds v4, and its card's configuration lacks three slots its §15 requires. The Target Operating Model and Delivery and Implementation mothers name their Library card v1 while the Library holds v3. The Process and Position Design mother maps the Library's test only at v2 while the card names TEST-PROCESS-AND-POSITION-DESIGN v4; the Delivery and Implementation mother keeps TEST-DELIVERY-AND-IMPLEMENTATION v1 while the card names v3. The Process and Position Design and Delivery and Implementation mothers cite older versions of the Target Operating Model in places | Each mother aligns at its next version |
| 9 | Protocol `org-aion-record.schema.json` | A draft on design stages that `49GAION/DR-0032` withdrew | None: moot (see the reading below) |

**Reading (49GAION DR-0041), 25 October 2026.** Draft 9 is moot: `49GAION/DR-0032` withdrew the stages it concerned, and the path of an `[ORG]AION` is the one of the complete definition (`49GAION/DR-0041`). Its number is kept, unproposed.
